# Publishing an iOS app to the App Store

Learned from shipping a 1.0.1 update of a SwiftUI app (SwiftData + RevenueCat + Firebase Crashlytics, project generated by xcodegen) in Oct 2026. The whole release — localization, listing, new version, build upload, and review submission — ran from the terminal with no fastlane and no App Store Connect MCP. Follow the phases in order.

## Ground rules

- **Never read, print, or paste the `.p8` private key.** Only pass its path to tools. The Key ID and Issuer ID are not secret, but keep them (and team IDs) out of public repos and skills.
- **Ask before:** creating an App Store version, uploading a build, changing a live listing, answering export compliance, and submitting for review. A user's "submit it" covers the submission steps in Phase 6, not new metadata changes.
- **Auto mode blocks deploy steps without a specific approval.** Uploading a build, attaching a build, and submitting were each blocked as a production deploy after a general "yes, do everything". They ran once the user's latest message named the action ("Attach build 1.1.0 (4) to version 1.1.0 … and submit for review now"). So ask one question that names the version, the build, and the action. Never retry a blocked step in another form; offer the exact command for the user to run instead.
- **Do not search the Mac for `.p8` files.** Auto mode blocks it as credential exploration. Ask the user for the Key ID, the Issuer ID, and the file path, then check only that path with `test -f`. A key used in an earlier session may have been moved since.
- Accepting agreements, creating API keys, and signing in to Xcode are the user's job.
- Before a commit, run `git status` and stage only the files you changed. Other sessions may have edited files in the same checkout. If an unexpected change gets into a commit, show the diff to the user and verify it (Phase 0, step 4 found such a change was a real fix).
- Keep an `appstore/` folder in the project: the API script and one `metadata/<locale>.json` per language. Commit it so the next release reuses it.

## Phase 0 — Inventory (Claude)

1. Tools: `command -v fastlane asc xcodegen`, `security find-identity -v -p codesigning`. Usually only an "Apple Development" identity exists. That is fine, because Phase 5 uses cloud signing.
2. Search the MCP registry for "app store connect". In Oct 2026 there was no connector, so use the App Store Connect API directly (Phase 1).
3. Project: `project.yml` (xcodegen) or the `.pbxproj`, `Info.plist`, `MARKETING_VERSION`, `CURRENT_PROJECT_VERSION`, `DEVELOPMENT_TEAM`, `knownRegions`, and existing `*.xcstrings` / `*.lproj`.
4. **Entitlement ID check:** grep for `entitlements["..."]` in iOS (and Android) code and compare with the RevenueCat entitlement `lookup_key` (`list-entitlements`). In one app the code used `"lifetime"` but the dashboard ID was `"<App> Pro"`, so paid users looked unpaid after a restart or restore.
5. **Listing claims against the code:** if the description says "zero analytics / no tracking", check that Firebase Analytics is off (`IS_ANALYTICS_ENABLED = false` in `GoogleService-Info.plist` and `Analytics.setAnalyticsCollectionEnabled(false)`). Crashlytics still sends crash reports, so "zero telemetry" is not true.
6. Public listing without credentials: `curl "https://itunes.apple.com/lookup?id=<appStoreId>&country=us"` (or `?bundleId=<bundle id>`) gives the name, live version, and description (not the subtitle or keywords). The next `MARKETING_VERSION` must be higher than the live version.
7. **Capabilities against the App ID:** `python3 -I xcloud.py --bundle-id <id> capabilities <App>.entitlements`. A capability added to the code (iCloud, Push, …) but not to the App ID builds fine on the Mac, because Xcode adds it there. On Xcode Cloud it breaks every archive export (Phase 5b).
8. **CloudKit:** if the entitlements use CloudKit, the user must deploy the schema to Production before the release, or sync fails for App Store users. CloudKit Console → **CloudKit Database** → the container → select the **Development** environment → **Deploy Schema Changes…** at the bottom of the left sidebar (hidden while Production is selected).

## Phase 1 — App Store Connect API access

**User steps** (they must be Account Holder or Admin):
1. appstoreconnect.apple.com → **Users and Access** → **Integrations** → **App Store Connect API** → **Team Keys**. The first time, click **Request Access**.
2. **Generate API Key** → give it a name → choose an access role → **Generate**.
3. The **Issuer ID** is above the table. The **Key ID** is in the key's row. **Download** the `.p8` file. Apple allows this only once.
4. Move the file to `~/.appstoreconnect/private_keys/AuthKey_<KEYID>.p8`. `xcodebuild` and `altool` look there automatically.

**Role choice:**
- **App Manager** can do all metadata, version, build, and submission work in this skill.
- App Manager **cannot cloud-sign for distribution**. The export then fails with `Cloud signing permission error` / `No signing certificate "iOS Distribution" found`. Fix: export with the Apple ID that is signed in to Xcode (Phase 5), or use an **Admin** key.

**First call fails with 403 `FORBIDDEN.REQUIRED_AGREEMENTS_MISSING_OR_EXPIRED`:** the Account Holder must accept the new agreement in App Store Connect → **Business** (or the banner at the top). Claude cannot accept terms. Wait for the user, then retry.

**Auth:** an ES256 JWT, `{"iss": issuer, "iat", "exp": iat + ≤20 min, "aud": "appstoreconnect-v1"}`, header `{"kid": keyId, "typ": "JWT"}`. Use `asc.py` from this skill. It has no dependencies and signs with `openssl`. For one-off queries, `import asc` and use `asc.call("GET", "/builds?…")`: paths are relative to `/v1`, so `"/v1/…"` gives a 404.

```bash
export ASC_KEY_ID=<key id> ASC_ISSUER_ID=<issuer id> ASC_KEY_PATH=~/.appstoreconnect/private_keys/AuthKey_<KEYID>.p8
python3 -I asc.py --bundle-id com.example.App status     # read-only: app infos, versions, localizations
python3 -I asc.py --bundle-id com.example.App builds     # read-only: builds, processing state, export compliance
python3 -I asc.py --bundle-id com.example.App create-version 1.0.1               # ask first
python3 -I asc.py --bundle-id com.example.App apply appstore/metadata/<locale>.json --dry-run
python3 -I asc.py --bundle-id com.example.App submit 1.0.1 1 --no-encryption     # ask first; Phase 6 in one step
```

## Phase 2 — Localize the app (if the release adds languages)

Users with a non-English device language saw English because the app had only `en` and no string catalog. To fix it (`<lang>` below is the new language code, for example `ja` or `de`):

- Add `Resources/Localizable.xcstrings` (`"sourceLanguage": "en"`). Generate it with Python from an `{english: translation}` dict, using `"extractionState": "manual"` and `stringUnit.state: "translated"`. Count the keys and validate the JSON.
- SwiftUI **string literals** in `Text("…")`, `Button("…")`, `Label`, `Section`, `TextField`, `.navigationTitle("…")`, and `.alert("…")` are already `LocalizedStringKey`. They only need catalog entries. Interpolation becomes a format key: `Text("\(n) words")` → `"%lld words"`, a `String` → `%@`.
- These are **not** localized and need code changes:
  - `String` variables and properties passed to `Text(x)` (error messages, feature lists, struct fields) → `String(localized: "…")` where the value is set, or `Text(LocalizedStringKey(x))`.
  - **Ternaries** such as `Text(flag ? "A" : "B")` resolve to `String`. Use `LocalizedStringKey("A")` on both sides.
  - Enum `rawValue` titles → `Section(LocalizedStringKey(group.rawValue))`.
  - Notification content, `LAContext.localizedReason`, `localizedFallbackTitle`.
  - **Seeded data** (built-in templates saved in SwiftData) → store English and localize when displayed: `isBuiltIn ? String(localized: String.LocalizationValue(name)) : name`. If you localize when seeding, the language is frozen at first launch.
- Permission strings → `InfoPlist.xcstrings`, keyed by `NSFaceIDUsageDescription` and the other usage-description keys.
- Add `CFBundleLocalizations: [en, <lang>]` (xcodegen `info.properties`) and `options.developmentLanguage: en`. After `xcodegen generate`, `knownRegions` must list the new language.
- **Hardcoded prices are wrong in other storefronts.** Show RevenueCat's `offerings().current?.lifetime?.localizedPriceString` (or `storeProduct.localizedPriceString`), and keep a fallback until offerings load. Then turn the price keys into format keys (`"Pay %@"`).
- Check the built `.app` contains `<lang>.lproj`. Run in that language without changing simulator settings:
  `xcrun simctl launch <udid> <bundleId> -AppleLanguages "(<lang>)" -AppleLocale <lang>_<REGION>`, then take screenshots of the main screens.
- If there is an Android app too, use the same terms on both platforms (for example the names of features and screens).

## Phase 3 — Version number

- Set `MARKETING_VERSION` to the new version (`1.0.1`). The build number (`CURRENT_PROJECT_VERSION`) can start at `1` again for each new marketing version.
- `MARKETING_VERSION` is set per target and configuration (app, widget/extensions, tests; Debug and Release). Change every entry: an extension version that differs from the app's is flagged at upload. Check both on the built product, e.g. `PlistBuddy … <App>.app/PlugIns/*.appex/Info.plist`.
- **xcodegen trap:** xcodegen writes a fixed `CFBundleShortVersionString = 1.0` / `CFBundleVersion = 1` into `Info.plist`, so `MARKETING_VERSION` is ignored. Add to `info.properties`:
  ```yaml
  CFBundleShortVersionString: "$(MARKETING_VERSION)"
  CFBundleVersion: "$(CURRENT_PROJECT_VERSION)"
  ```
  Verify on the built product: `/usr/libexec/PlistBuddy -c "Print CFBundleShortVersionString" <App>.app/Info.plist`.

## Phase 4 — App Store version and listing (API)

- **Only one version can be in progress.** While a version is `WAITING_FOR_REVIEW` or `IN_REVIEW`, you cannot create the next one. Either wait for the result, or remove the version from review (it becomes `DEVELOPER_REJECTED`), change its `versionString`, attach the new build, and resubmit. That loses its place in the review queue, so ask the user first.
- A **live version is not editable**. Name, subtitle, description, keywords, and screenshots change only with a new version. Only `promotionalText` can change at any time.
- Create the version (ask first): `POST /v1/appStoreVersions` `{platform: IOS, versionString}` → state `PREPARE_FOR_SUBMISSION`. No build is needed yet, so create it and write the listing while the build runs. This also creates a second, editable **AppInfo** (`PREPARE_FOR_SUBMISSION`) next to the live one (`READY_FOR_SALE`).
- Two levels of localization:
  - `appInfoLocalizations` (on the editable AppInfo): `name`, `subtitle`, `privacyPolicyUrl`.
  - `appStoreVersionLocalizations` (on the version): `description`, `keywords`, `promotionalText`, `whatsNew`, `supportUrl`, `marketingUrl`.
- Creating a new `appInfoLocalization` for a locale **also creates an empty version localization**. So "create-or-update" by locale, and PATCH when one exists.
- The new version copies `description`/`keywords`/URLs from the live version but **not `promotionalText` or `whatsNew`**. Copy the promo text over. `whatsNew` is required for updates.
- Limits: name 30, subtitle 30, keywords 100 (comma-separated, no spaces needed), promotional text 170, description 4000. Count with Python `len()` before upload. Locale codes are App Store codes: `en-US`, `en-CA`, `ja`, `zh-Hans`, and so on.
- Translate from the **live** English text (read with `status`), not from memory. Remove storefront-specific prices ("$7.99") from translated descriptions. Do not repeat a claim the code makes false.
- Screenshots: a locale without its own screenshots uses the primary language's screenshots, so a new language can ship without new screenshots. To make localized ones, see Phase 4b.
- After every write, read the data again with `status` and show the result to the user.

## Phase 4b — Localized screenshots

Make one captioned set for the primary language and one for each localized language. Storefronts without their own set show the primary set.

**Size and simulator**
- Upload the 6.9" iPhone size, 1320×2868 (`APP_IPHONE_67`). Apple scales it for smaller iPhones, so remove the old `APP_IPHONE_65` set.
- Use a Pro Max simulator for this app only (`iPhone <N> Pro Max - <App>`). The newest runtime may refuse Pro Max device types (`simctl create` → `Incompatible device`). Then create it on the previous runtime. Check one capture with `sips -g pixelWidth -g pixelHeight`.
- Fix the status bar first: `xcrun simctl status_bar <udid> override --time 9:41 --dataNetwork wifi --wifiMode active --wifiBars 3 --cellularMode active --cellularBars 4 --batteryState charged --batteryLevel 100`.
- Build with the default DerivedData. A `-derivedDataPath` inside the project made the Crashlytics run script fail with `Operation not permitted` under script sandboxing.

**Repeatable captures with Debug launch arguments**
Taps in the simulator need the user's permission and differ per language. Add `#if DEBUG` launch arguments instead, so one script captures every screen in every language:
- `-seedScreenshotData`: fill realistic sample data (birth date, entries, events …) and turn on the debug Pro bypass. Write the sample text in the language the app runs in (`Bundle.main.preferredLocalizations.first`). Mark the seed type `@MainActor` when it changes `@MainActor` objects; Xcode 27.1 fails the build otherwise.
- `-screenshotScreen <name>`: open one sheet or screen from the root view's `.onAppear` (set the `@State` that presents it). Skip the review prompt when it runs.
- An image the app renders (a share card) can be written to `Documents/` and copied out with `xcrun simctl get_app_container <udid> <bundleId> data`.
- Loop per language: `xcrun simctl terminate`, then `xcrun simctl launch <udid> <bundleId> -seedScreenshotData -screenshotScreen <name> -AppleLanguages "(<lang>)" -AppleLocale <lang>_<REGION>`, wait ~5 s, `xcrun simctl io <udid> screenshot raw/<locale>/<name>.png`.
- Keep the script as `appstore/screenshots/capture.sh <udid>`.

**Framing** (`appstore/screenshots/make_screenshots.py`, Pillow)
- macOS Python has no Pillow, and the system Python refuses `pip install`. Use a venv: `python3 -m venv ~/.venvs/screenshots && ~/.venvs/screenshots/bin/pip install pillow`.
- Layout per image: a vertical gradient taken from the app icon colors, a bold title (~112 px, `/System/Library/Fonts/SFNS.ttf` with variation `Bold`), a one-line or two-line subtitle (~52 px), then the capture scaled to 80 % with ~96 px rounded corners, a thin bezel and a soft shadow, running off the bottom edge. Show a share image whole, like a card, not in a phone.
- `CAPTIONS = {locale: [(title, subtitle), …]}`, one entry per screen in App Store order. The first three screens matter most: lead with the core screen.
- SF covers Latin scripts with diacritics. Japanese needs Hiragino (`ヒラギノ角ゴシック W7.ttc` / `W4.ttc`) and wrapping by character.
- Read a contact sheet of all images in every language before you finish. Rewrite any title or subtitle whose last line is one word; translated captions are often longer than the English ones.
- Folder names are App Store locale codes: `raw/<locale>/` and `out/<locale>/`. Name the primary set after the app's primary locale (read it with `status`; it may be `en-CA`, not `en-US`).
- Commit `capture.sh`, `make_screenshots.py` and `raw/`. Add `out/` to `.gitignore`, because it is generated.

**Upload** (ask first; it replaces the version's screenshots)
- The version must be editable, and each locale must already have an `appStoreVersionLocalization`. Apply the metadata files first.
- Per locale: `GET /appStoreVersionLocalizations/{id}/appScreenshotSets`, delete the `APP_IPHONE_67` and `APP_IPHONE_65` sets, `POST /appScreenshotSets` `{screenshotDisplayType: APP_IPHONE_67}` with the localization relationship.
- Per image: `POST /appScreenshots` `{fileName, fileSize}` with the set relationship, send each `uploadOperations` chunk (its `method`, `url` and `requestHeaders`), then `PATCH /appScreenshots/{id}` `{uploaded: true, sourceFileChecksum: <md5 hex>}`.
- Poll `assetDeliveryState.state` until every image is `COMPLETE` (or `FAILED`). Images upload in file-name order, so name them `1.png` … `6.png`.
- Support `--dry-run` that prints what each locale would delete and upload. Run it and show the output before the real run.

## Phase 5 — Archive and upload (ask first)

```bash
xcodegen generate   # if the project uses it
xcodebuild archive -project App.xcodeproj -scheme App -configuration Release \
  -destination 'generic/platform=iOS' -archivePath build/App-1.0.1.xcarchive -allowProvisioningUpdates
```

`ExportOptions.plist`:
```xml
<dict>
  <key>method</key><string>app-store-connect</string>
  <key>destination</key><string>upload</string>
  <key>teamID</key><string>TEAMID</string>
  <key>signingStyle</key><string>automatic</string>
  <key>uploadSymbols</key><true/>
  <key>manageAppVersionAndBuildNumber</key><false/>
</dict>
```

```bash
xcodebuild -exportArchive -archivePath build/App-1.0.1.xcarchive \
  -exportOptionsPlist ExportOptions.plist -exportPath build/export -allowProvisioningUpdates
```

- **Without** `-authenticationKeyPath/-authenticationKeyID/-authenticationKeyIssuerID`, xcodebuild uses the Apple ID that is signed in to Xcode. This account can cloud-sign, so no local distribution certificate is needed. **With** an App Manager key it fails (see Phase 1). With an Admin key, the flags allow a run with no Xcode account.
- Success ends with `Upload succeeded` / `** EXPORT SUCCEEDED **`.
- `Upload Symbols Failed ... FirebaseAnalytics.framework / GoogleAppMeasurement*.framework` warnings come from Google's prebuilt binaries. They are harmless.
- Before upload, check the archive: `Info.plist` version and build, and `<lang>.lproj` folders present.
- Processing takes about 2–30 minutes. Check `GET /v1/builds?filter[app]=<appId>&sort=-uploadedDate&include=preReleaseVersion` until `processingState == VALID`. Note: `filter[preReleaseVersion.version]` returned nothing; use `include` and match the version instead.

## Phase 5b — Automated builds with Xcode Cloud (alternative to Phase 5)

Verified Oct 2026: a pushed tag `v1.0.2` archived on Xcode Cloud and reached App Store Connect as `1.0.2 (1)`, state `VALID`. The whole run took about 7.5 minutes, and the build was uploaded before the run was marked complete.

**What the API can and cannot do** (App Store Connect API reference):

| Resource | API |
|---|---|
| `ciProducts` (Xcode Cloud product) | read, delete. **No create.** |
| `scmProviders`, `scmRepositories` (GitHub connection) | **read only** |
| `ciWorkflows` | create, update (PATCH), delete |
| `ciBuildRuns` | start a build (POST) |

So the first setup must happen once in Xcode. After that, `xcloud.py` (in this folder) does the rest.

**One-time setup in Xcode** (Integrate → Create Workflow…):
1. Select the app product, then **Next**.
2. **Connect Source Code Repository:** press **Connect…** for the primary repo only. The user signs in to GitHub and installs the Xcode Cloud GitHub app on that repo. Public package repos (Google, RevenueCat, …) do not need connecting; **Next** is enabled as soon as the primary repo is connected. Their **Connect…** opens a GitHub app-install page for someone else's repo, so tell the user to close it.
3. **Confirm Existing App** (matched by bundle ID) → **Setup Complete**. Do **not** press **Start First Build**.
4. Commit the new `<App>.xcodeproj/xcshareddata/xcodecloud/manifest.json`.

**Traps:**
- Setup saves a workflow named **Default** with a **Branch Changes** trigger on `main` and a **Build** action. It builds on every push until you change it.
- Scripting Xcode's workflow editor through Accessibility did not work for deleting start conditions; neither Delete nor ⌘⌫ removed them. Edit the workflow through the API instead.
- **"Latest Release" Xcode can lag behind.** On release day it still meant Xcode 27.0 while 27.1 was listed separately. Pin the exact version when the app needs a newer SDK (`xcloud.py xcode` lists them).
- `buildDistributionAudience: INTERNAL_ONLY` builds can never be submitted to the App Store. Use `APP_STORE_ELIGIBLE`.
- **`audience=None` (Deployment Preparation "None") archives but never uploads.** Runs show `SUCCEEDED`, yet nothing reaches TestFlight, and the archive keeps the project's `CURRENT_PROJECT_VERSION`. `show` prints the audience. To ship such a run without changing the workflow, download its archive (`artifact N ARCHIVE <new dir>`) and upload it with Phase 5's `-exportArchive` (ask first). The binary keeps the release Xcode that built it (`DTXcode` in its `Info.plist`), which avoids the beta-Xcode problem below.
- With `APP_STORE_ELIGIBLE`, Xcode Cloud numbers builds from 1 for each new version.
- Builds made with a **beta** Xcode can go to TestFlight but cannot be submitted for review. Check `DTXcodeBuild` in the archive's `Info.plist` before Phase 6.
- Without `ITSAppUsesNonExemptEncryption` in `Info.plist`, every build waits for an export-compliance answer (see Phase 6, step 1).

**Turn Default into a tag release workflow:**

```bash
python3 -I xcloud.py --bundle-id com.example.App show                      # workflow ID, current triggers
python3 -I xcloud.py --bundle-id com.example.App tag-release <WORKFLOW_ID> --scheme App --xcode "Xcode 27.1"           # dry run
python3 -I xcloud.py --bundle-id com.example.App tag-release <WORKFLOW_ID> --scheme App --xcode "Xcode 27.1" --apply   # ask first
```

This sets: start on tags with prefix `v`, manual start on tags only, no branch trigger, one **Archive – iOS** action with `APP_STORE_ELIGIBLE`, and the pinned Xcode.

The `PATCH` can return **500 `UNEXPECTED_ERROR` and still apply** (seen twice in Oct 2026). Before you retry, run `show` and check the workflow.

**Version from the tag:** copy `ci_post_clone.sh` (in this folder) to `<repo>/ci_scripts/ci_post_clone.sh`, set `PROJECT`, `chmod +x`, and commit. It reads `CI_TAG` (`v1.0.2` or `refs/tags/v1.0.2`) and writes `MARKETING_VERSION` into `project.pbxproj`. Test it locally on a scratch clone with `CI_TAG=v1.0.2 CI_PRIMARY_REPOSITORY_PATH=<clone> ci_scripts/ci_post_clone.sh`, then check `xcodebuild -showBuildSettings | grep MARKETING_VERSION`.

**Release and watch:**

```bash
git tag v1.0.2 && git push origin v1.0.2                 # ask first: this uploads a build
python3 -I xcloud.py --bundle-id com.example.App runs 1      # run, actions, and the App Store Connect build
```

Poll `runs` about once a minute. When the run is `COMPLETE SUCCEEDED`, `runs` also shows the build's `processingState`; continue with Phase 6 once it is `VALID`. `xcloud.py start <WORKFLOW_ID> --tag v1.0.2` (or `--branch main`) starts a clean build through the API; `--branch` was verified in Oct 2026.

**When runs fail** (verified Oct 2026, every run failed for two days):

```bash
python3 -I xcloud.py --bundle-id <id> runs 10                          # when did failures start, which commit
python3 -I xcloud.py --bundle-id <id> issues <N>                       # ERROR lines of run N
python3 -I xcloud.py --bundle-id <id> artifact <N> LOG_BUNDLE <new dir>
# then read app-store-export-archive-logs/xcodebuild-export-archive.log and */IDEDistributionProvisioning.log
```

| Log says | Cause | Fix |
|---|---|---|
| Compile `error:` in a package (e.g. RevenueCat `init(stringRepresentation:)`) | Package too old for the Xcode version | Raise the package's `minimumVersion` in the `.pbxproj` `XCRemoteSwiftPackageReference`, run `xcodebuild -resolvePackageDependencies`, commit both files |
| `Exporting for App Store Distribution failed` → `Automatic signing cannot update bundle identifier "<id>"` + `No profiles for '<id>' were found` | The entitlements need a capability the App ID does not have; Xcode Cloud may not add it. The widget/extension still gets its profile | `capabilities <App>.entitlements` lists what is missing. Then (ask first) run Phase 5's local `xcodebuild archive … -allowProvisioningUpdates` with the Apple ID signed in to Xcode: it adds the capabilities and registers the iCloud container. The public API cannot assign iCloud containers. Do not upload that local archive; re-run Xcode Cloud |

- `Unable to authenticate with App Store Connect (… Session Proxy Provider …)` appears in failing and in succeeding exports. It is not the cause; read on to the `error: exportArchive` lines.
- `issues` only says "download the logs artifact"; the cause is always in the log bundle.

**No post-actions through the API:** TestFlight tester-group distribution (a post-action) cannot be set through `ciWorkflows`. Add it in Xcode or App Store Connect if needed, or enable automatic distribution on the internal group.

## Phase 6 — Submit for review (ask first)

1. Export compliance: `PATCH /v1/builds/{id}` `{"usesNonExemptEncryption": false}` when the app uses only HTTPS / Apple crypto. Check that earlier builds used the same answer. Better: add `ITSAppUsesNonExemptEncryption: false` to `Info.plist`, and the question never comes up again.
2. Attach the build: `PATCH /v1/appStoreVersions/{versionId}/relationships/build` `{"data": {"type": "builds", "id": buildId}}`.
3. `POST /v1/reviewSubmissions` `{platform: IOS}` + relationship `app` → state `READY_FOR_REVIEW`.
4. `POST /v1/reviewSubmissionItems` with relationships `reviewSubmission` and `appStoreVersion`.
5. `PATCH /v1/reviewSubmissions/{id}` `{"submitted": true}` → `WAITING_FOR_REVIEW`.
6. Verify: `GET /v1/appStoreVersions/{id}?include=build` → `appStoreState: WAITING_FOR_REVIEW` and the correct build.
7. Tell the user the `releaseType` (default `AFTER_APPROVAL` = goes live automatically). They can change it to `MANUAL` before approval. Review usually takes 24–48 h.

Age rating, App Privacy, pricing, and content rights carry over from the earlier version. Re-check App Privacy if the release adds SDKs or data collection. If the app uses CloudKit, confirm with the user that the schema is deployed to Production (Phase 0, step 8) before you submit.

## Phase 7 — Wrap up

- Commit `appstore/metadata/*.json`, the script, and the version bump. Only stage your own files.
- With Xcode Cloud, also commit `ci_scripts/` and `xcshareddata/xcodecloud/manifest.json`, and record the product and workflow IDs (not the key) in project notes.
- Tell the user to move the `.p8` out of `~/Downloads` if it is still there.
- Note what is not done: the review result, screenshots per language, and the Android/Play counterpart (see `publish-android-play`).
